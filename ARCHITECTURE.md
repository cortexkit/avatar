# Architecture

Avatar draws an agent as a creature. The creature comes from three fields stored on the agent's record in a host's registry: `avatar_genome` (bytes, stored as hex), `avatar_type` and `avatar_version`. A mood is added at draw time. The same genome, type, version and mood always produce the same render tree, byte for byte, on every platform. A finished image drawn from it is byte-identical on any one platform, and agrees across platforms within a small tolerance (see Determinism).

Avatar is a library. It has no service, no store and no wire surface, and it never decides which genome an agent has. The registry that stores agents writes a new agent's genome when the agent is created, for example 16,384 random bytes as `creature.wild` (every byte pattern is a valid creature). Apps and tools read the record and render it with this code. Renders and caches must key on the stored record, never on the agent id: a genome can be re-rolled.

Two decisions carry the design:

- **One generator per type, written once, in Rust** (`crates/avatar-svg` for classic and wild, and one `crates/avatar-<stem>` crate for each newer type). Consumers receive the finished render tree or image and draw it; nobody writes a second copy of a generator. Comparing independent implementations against a corpus checks a sample of a huge input space, so it cannot prove they agree on rare features (`docs/design/011-port-surface.md`). Apple-platform apps run this Rust themselves, through an embedded static library in the Swift package.
- **Platform-invariant arithmetic.** A creature's tree must be byte-identical everywhere, so no generation path calls the platform maths library. See Determinism.

## Terms

- **Genome:** the stored bytes. `creature.classic` uses 1,024 bytes (2,048 hex characters); `creature.wild` and the six newer types use the same 16,384 bytes (32,768 hex characters), so a row changes look by changing only its type. A wild genome derived from an id begins with the classic genome derived from the same id (`derive_genome_bytes` in `crates/avatar-genome/src/identity.rs`).
- **Type:** which representation draws a genome. Registered types are `creature.classic`, `creature.wild`, `creature.wild-plus`, `creature.sprouts`, `creature.pixel-critters`, `creature.knitted-toys`, `creature.small-robots` and `creature.drawn-heads` (`crates/avatar/src/dispatch.rs`). A type's stem is its name without `creature.`; the six newer types' generators live in `crates/avatar-<stem>`. A new look is a new type.
- **Version:** one generation of a type's generator. It exists to fix generation bugs. Every row renders at the version it stores, so versions are added and never edited (`docs/design/012-version-and-type-procedure.md`). Today: classic 2, wild 2, and 1 for each of the six newer types. Wild version 1 still draws every row that stores it; version 2 exists because version 1 draws mood lids and squints beside eyes that the creature's eye aspect or the mood has scaled (`wild::Generation` in `crates/avatar-svg/src/wild/mod.rs`). A type no agent uses yet may still change in place, because no agent has a creature of that type whose look it would change.
- **Mood:** one of seven render-time moods: neutral, working, happy, waiting, blocked, sad, sleepy. A mood changes face geometry, never identity or colour, so a render cache must key on it.
- **Phenotype:** classic only. Typed fixed-unit parameters decoded from a classic genome (`crates/avatar-phenotype`), with a canonical JSON form. Wild decodes its genome straight into its own `Creature` struct.
- **Render tree:** the output of every generator: a flat, painter-order list of primitives (shapes, paths, paints, strokes, transforms, effects) in `crates/avatar-svg/src/tree.rs`. `canvas` is the SVG viewBox edge; coordinates are 100 times finer, so divide by `RenderTree::extent()`, never by `canvas`. Classic draws on a 10,000-unit canvas; wild, wild-plus, sprouts, small robots and drawn heads on 240; knitted toys on 200; pixel critters on 24, one unit per cell of its pixel grid.
- **Label and role:** a primitive's `label` is a diagnostic name with no stability promise. Its `role` is the only thing a consumer may key behaviour on. The one role so far is `ground_shadow`. Each wild creature has exactly one; wild-plus, sprouts, knitted toys and small robots mark their ground shadow with it; classic, pixel critters and drawn heads draw none. A client with no ground plane hides it.

## Code map

| Layer | Where | Role |
|---|---|---|
| Tables | `crates/avatar-tables` | Committed lookup tables (quarter-wave sine `SIN_QUARTER`, five `EASE_*` tables), `sin_q30`/`cos_q30`, the rounding division `div_round_half_away`, and the `mint` binary that regenerates or checks the tables. |
| Phenotype | `crates/avatar-phenotype` | Classic's typed units (`Milli`, `Q32`, `Bam16`, `Rgb`), the `Phenotype` struct and its canonical JSON. |
| Genome | `crates/avatar-genome` | The classic 1 KiB `Genome`, its decoder to `Phenotype`, the palette table, and identity derivation from an id at any length. |
| Generators and tree | `crates/avatar-svg` | The classic generator (`build.rs`, `geometry.rs`, `face.rs`, `eyes.rs`, `brows.rs`, `mouth.rs`, `lashes.rs`, `pattern.rs`, `mood.rs`), the wild generator (`src/wild/`), the tree, canonical tree JSON and both SVG serializers. |
| Newer generators | `crates/avatar-wild-plus`, `avatar-sprouts`, `avatar-pixel-critters`, `avatar-knitted-toys`, `avatar-small-robots`, `avatar-drawn-heads` | One crate per newer type. Each exposes `render_tree` (genome and mood to tree; knitted toys, small robots and drawn heads also draw less detail for a small size) and `decode` (its typed traits), and builds its tree with `avatar-svg`'s tree types. |
| Rasterizer | `crates/avatar-raster` | Turns a tree, through its SVG, into RGBA pixels (`rasterize_tree`, `rasterize_svg`), optionally dropping the ground shadow. |
| Dispatch | `crates/avatar` | The one crate a Rust host depends on. `dispatch.rs` routes a stored row's type and version to the generator that draws it, and holds the type constants and `render_image`; the crate root re-exports the tree types, image types and serializers. |
| C boundary | `crates/avatar-ffi` | `avatar_render_tree_json`, returning canonical tree JSON, and `avatar_render_image`, returning RGBA pixels, each with a distinct status per failure; panics are contained. |
| Swift | `ports/swift`, `Package.swift` | AvatarKit: calls the embedded core, decodes the tree, owns a cache, composes transforms. Ships the committed `AvatarCore.xcframework`. |
| TypeScript | `ports/ts` | A fail-closed tree decoder and the generic SVG serializer. No generator. |
| Export | `crates/avatar-export` | CLI: renders a stored genome to PNG, SVG or tree JSON, and mints genome manifests. |
| Corpus | `crates/avatar-vectors`, `vectors/` | Golden vectors and the tests that pin every boundary. |
| Review harness | `playground/` | Grids, review sheets, the placement-invariant checker and the browser lab. Not shipped. |
| Gate | `scripts/check.sh` | The only gate. See The gate. |

`STRUCTURE.md` has the directory map and where to add new code.

The library crates have prefixed package names, the names they are published under: `cortexkit-avatar-tables`, `cortexkit-avatar-phenotype`, `cortexkit-avatar-genome`, `cortexkit-avatar-svg`, `cortexkit-avatar-raster`, `cortexkit-avatar`, and `cortexkit-avatar-<stem>` for each newer type. Each keeps its short library name: code imports `avatar_tables`, `avatar_phenotype`, `avatar_genome`, `avatar_svg`, `avatar_raster`, `avatar` and `avatar_<stem>` (with `_` for `-`, as in `avatar_wild_plus`). Cargo commands that select a package use the prefixed name (`cargo test -p cortexkit-avatar-svg`). `avatar-ffi`, `avatar-export` and `avatar-vectors` are never published.

## Rendering a stored avatar

1. The caller holds the row's bytes, type and version, plus a mood.
2. `render_tree_for_bytes` checks the type, then the version, then the genome length that type needs. The order is a contract. An unknown type or version means "this build cannot draw it": the client draws nothing and stays quiet. A wrong length for a known type means the row is malformed: the client reports it. Checking length first would report every row of a newer, differently sized type as corrupt.
3. Classic v2: `avatar_genome::decode` gives a `Phenotype`, and `build_render_tree` builds the tree. Wild v1 and v2: `wild::decode_genome` reads each feature from fixed region offsets (body bytes 0..64, extremities 64..160, palette and face from 160, surface sites 240..304), and `draw_full` builds the primitives for the `wild::Generation` the version names. The six newer types at version 1: the type's own crate decodes the genome and draws the tree with its `render_tree`. Each takes its body colour from the genome bytes wild takes it from (wild-plus keeps wild's whole body as its head). `render_tree_for_bytes` draws full detail; `render_tree_for_bytes_at` and `render_image` pass the size on, so knitted toys, small robots and drawn heads leave out fine detail and keep lines about a pixel wide when drawn small. A size of 0 draws full detail.
4. The tree leaves through one of three projections: `serialize_tree_json` (the canonical JSON every consumer decodes), `serialize_tree` (generic SVG; `serialize_tree_with_id_prefix` when several creatures share one document), or `serialize_svg` (classic only, the historical SVG layout its corpus pins). The JSON writes each distinct mask once, in a top-level `masks` table that masked effects name by index (`mask_ref`), because wild creatures clone one body mask into many primitives and the full copies made up most of a wild tree's bytes. Decoders resolve the references back into inline masks, so the in-memory tree is the same in every language (`docs/design/006-render-tree.md`).

How each consumer gets there:

- **Apple-platform apps:** AvatarKit's `renderTreeViaCore(genomeBytes:type:version:mood:)` calls the embedded core, then decodes the JSON with `decodeRenderTreeJson` (`RenderTree.swift`), which first checks the integer-only number grammar with the strict parser in `RenderTreeJSON.swift`. Each core status maps to its own `CoreRenderError`. `RenderTreeCache` is owned by the host app, keyed by bytes, type, version and mood, and can be emptied under memory pressure. `TreeAffine.swift` composes decoded transforms with the pinned sine table and a fixed-point multiply; it builds no geometry.
- **Rust hosts:** depend only on the `cortexkit-avatar` package (its library is imported as `avatar`), from crates.io or by git at a pinned commit, and call `render_tree_for_bytes` and `serialize_tree`, or `render_image` for finished RGBA pixels. It re-exports the tree types, `Mood` and the serializers, so rendering needs no other avatar crate.
- **Finished images:** `render_image`, the C boundary's `avatar_render_image` and AvatarKit's `renderImageViaCore` draw a stored row at a size in pixels. This is how apps show the six newer types: their trees use tree features only Rust draws (a positioned radial gradient, stop opacity, compound paths, a pixel grid), which the Swift and TypeScript decoders refuse. `render_image(genome_bytes, avatar_type, version, mood, size_px, options)` checks the type, version and genome length as above, then that `size_px` is 1 to 2,048 (`MAX_SIZE_PX`). It draws the tree at the detail for `size_px`, as `render_tree_for_bytes_at` does, and rasterizes it with `avatar_raster::rasterize_tree`. It returns an `Image`: `size_px`, the `alpha` form and `pixels`, exactly `size_px² × 4` bytes of sRGB RGBA8, rows top first and tightly packed. `ImageOptions` holds two choices. `ground_shadow` is `Keep` (the default) or `Drop`, which leaves out every primitive whose role is `ground_shadow`. `alpha` is `Premultiplied` (the default) or `Straight`, converted in integers, with a fully transparent pixel `[0, 0, 0, 0]`. The image is a pure function of the arguments, with no cache or global state, so it is safe from several threads and a host may cache it by every argument. `render_tree_for_bytes_at` takes a `detail_px`, and 0 means full detail: the tree `render_tree_for_bytes` returns.
- **TypeScript:** `decodeRenderTreeJson` and `serializeTree` in `ports/ts/src`.
- **Images:** `avatar-export --genome-file <path> --type <type> --version <n> --out <file>`. The `--out` extension picks the format: `.png` or none, `.svg`, or `.json`; any other extension is refused. Live agents always render their stored genome. `--mint-genomes` writes a manifest of id-derived genomes for a type. A wild genome does not fit on a Windows command line, so portable callers use `--genome-file` (`-` reads standard input) rather than `--genome <hex>`.

No consumer may normalise a creature's visual weight (cropping to alpha bounds, scale nudges, minimum sizes): how much ink a creature has is part of who it is.

## Determinism

- **creature.classic** is integer-only: `i64` milliunits on a 1,000,000-unit canonical canvas, Q32.32 factors, 16-bit binary angles, sine and cosine from the committed quarter-wave table, easing from committed tables, and one rounding helper, `div_round_half_away`.
- **creature.wild** uses `f64`, restricted to operations IEEE 754 makes exact everywhere: `+ - * /`, `sqrt`, comparisons and Rust's half-away-from-zero `round`. Sine, cosine, tangent and arctangent are rebuilt from those in `src/wild/math.rs`. `crates/clippy.toml` refuses maths-library calls (`sin`, `atan2`, `powf`, `mul_add` and the rest) under `-D warnings`; the standard functions appear only as test oracles. This matters because a wild creature takes branches on computed values: in measurement, a difference in the fourteenth digit flipped a branch and moved one creature by 93 canvas units.
- **The six newer types** follow the same rules as wild: `f64` with only the exact operations, and any trigonometry from `wild::math`.
- **Finished images** are not byte-identical across platforms. The rasterizer (resvg, drawing with tiny-skia) is outside the rules above: when tiny-skia clips a cubic curve at the edge of the area it draws, its cubic root solver (`roots_real` in tiny-skia's `src/path64/cubic64.rs`) calls the platform's `acos` and `cos`, and Apple's maths library and glibc can differ in the last bit. On the golden images that moved one pixel of one small-robots image by 6/255 between macOS and Linux. So an image is byte-identical on any one platform, and across platforms it agrees within one rule: identical, or no channel more than 8/255 off on at most max(1, 0.1%) of its pixels (`scripts/wild-port/compare_images.py`). Trees stay byte-identical everywhere.
- **Measured:** `scripts/wild-cross-platform.sh` runs natively on macOS arm64 and in Linux arm64 and x86_64 containers. With no argument it mints every type's corpus trees (wild's 25 and each newer type's 18) and compares them byte for byte, one type at a time, so the file names the corpora share are never pooled: each platform against macOS, and macOS against the type's committed trees. `scripts/wild-cross-platform.sh image` draws every golden image in `vectors/image/` with the `image-hashes` example of `crates/avatar` and compares each with its golden under the rule above, counting for each platform the images that are identical and those only within the tolerance. Windows x86_64 output from the same example can be passed in. The script needs Docker, so it runs by hand, and again on the exact commit before a release tag.
- **Committed data:** the lookup tables (`crates/avatar-tables/src/generated/`), the classic palette (`crates/avatar-genome/src/generated/`) and the classic Voronoi masks (`crates/avatar-svg/src/generated/`). Each has a mint binary. The gate runs the tables mint with `--check`, which compares and writes nothing.

## Conformance

The golden corpus lives in `vectors/`. The mint test in `crates/avatar-vectors` writes it; nobody edits it by hand.

- **Genome to phenotype:** `dna/` to `phenotype/`, 22 classic genomes.
- **Phenotype to classic SVG:** `svg/`, 40 genome and mood cells.
- **Tree to canonical JSON:** `tree/`, 65 trees (40 classic, 25 wild). This pins the transport every consumer decodes.
- **Tree to generic SVG:** `tree-svg/`, the same 65. This pins the drawing every consumer must reproduce.
- **Wild references:** `vectors/wild/` holds 12 genomes derived from the fixed ids in `corpus.tsv`, and its manifest. Each `corpus.tsv` row and manifest entry names the wild version its trees render at. The tests render every reference genome in every mood at version 1, and one of them, `wild-port-0022`, at version 2 too. 25 of those renders are pinned as tree files: 18 at version 1, and the seven version 2 moods of `wild-port-0022`, named `<id>__v2__<mood>.json`. A further test checks that on every reference genome in every mood, version 2 differs from version 1 only in where the lids and squints sit.
- **Newer types:** `vectors/<stem>/` holds each newer type's corpus at version 1: 18 trees in `tree/` and `tree-svg/`: the 12 wild reference genomes (read from `vectors/wild/`, not copied) in neutral, plus the other six moods of `wild-port-0005`. A test in the type's own crate mints them and checks the directory's exact contents. These trees live outside `tree/` and `tree-svg/` because the Swift and TypeScript decoders read those and refuse the newer types' tree features.
- **Finished images:** `vectors/image/` holds 137 golden PNGs and their manifest, each 8-bit RGBA with the pixels written verbatim (premultiplied ones stay premultiplied). The 47 classic and wild cells are the twelve wild genomes at version 1 in neutral at 16, 256 and 1,080 px; `wild-port-0022` at version 2 in all seven moods, and in neutral under all four option combinations, at 256 px; and classic `all_zero` at 256 px. Each newer type adds 15 at 256 px: its twelve corpus genomes in neutral, and `wild-port-0005` in neutral under the other three option combinations. `avatar-vectors` mints each one with `rasterize_tree` from a committed tree file, so the goldens do not depend on the `render_image` call they test. The tests check that `render_image` draws exactly what `rasterize_tree` draws from the committed tree on the platform running them, and that this image matches its golden under the cross-platform rule in Determinism.
- `vectors/contact-sheet.html` is regenerated with the corpus and byte-checked, so the visual review sheet cannot drift from the vectors.
- **Classic coverage:** the `fleet_coverage` example decodes 1,000 synthetic genomes and fails when a classic decode branch has no corpus vector.

The consumers are checked against the same files. Swift decodes every tree and re-encodes it to identical bytes, and its embedded-core tests reproduce every classic and wild tree through the binary. TypeScript decodes every tree and serializes each one to its `tree-svg/` file.

The browser lab (`playground/web/index.html`) is a JavaScript twin of the wild generator, used to review designs. `scripts/drift-check.sh` compares what the lab draws with the Rust generator over 24 seeds, and `scripts/const-drift.py` compares the sets of numeric constants in both. The two checks have complementary blind spots: the constant scan cannot see two existing values swapped, and the geometry comparison sees only the seeds it samples.

## The gate

`scripts/check.sh` is the repository's only gate. CI runs only when started by hand, and the untracked `.git/hooks/pre-push` runs the gate on every push except branch deletions.

- By default every cargo stage, the Python checks and the Rust half of the lab comparison run as one job on a Linux build server (`check.sh --linux`), sent there by the build-server client `ck` (a maintainers' tool that is not published) within a 600-second limit that covers queueing and retries. The workstation runs the embedded core's freshness check, the browser half of the lab comparison (with `chrome-headless-shell`), TypeScript, and the Swift suite where Swift is installed.
- Without `ck` the gate refuses. `AVATAR_GATE_LOCAL=1` runs every stage on the workstation, and is how to run the gate without that build server; it is never chosen automatically.
- Build-server jobs cannot write git-tracked files, so no gate stage writes one. Mints that rewrite tracked files run in a worktree.

## The embedded core

`ports/swift/AvatarCore.xcframework` is committed (static libraries for ios-arm64, ios-arm64-simulator and macos-arm64), so the app needs no Rust toolchain. Each static library is about 4.1 MB, up from 2.1 MB before the six newer types' generators were linked in. `scripts/build-xcframework.sh` builds it on macOS with Xcode. `ports/swift/AvatarCore.source-hash` records a hash of every source the binary is built from (`scripts/xcframework-source-hash.sh`). The gate refuses when the hash no longer matches, because every test builds from source and would pass on a stale binary. Rebuild it whenever the Rust it embeds changes; rebuilds of the same source are byte-identical.

## Error handling

Everything fails closed. No path falls back to a default or newest creature.

- `DispatchError`: `UnsupportedType`, `UnsupportedVersion` (both: draw nothing, quietly), `GenomeLength` (a malformed row: report it), and `Render(RenderError)`, where `RenderError` is `UnsupportedGrowth` or `UnsupportedCanvas` for classic render inputs outside their pinned values. Only `render_image` returns the other two, and only for a row it accepted: `ImageSize { requested }` for a size outside 1 to 2,048 pixels, and `Raster(RasterError)` when the rasterizer cannot draw the tree.
- The C boundary returns 0 for success, then one status per case: unknown type, unknown version, genome length, unknown mood, invalid argument, render error, panic. `avatar_render_image` returns invalid argument for a null argument, a flag other than 0 or 1, or a size outside 1 to 2,048, and render error for a rasterizer failure; after any failure its outputs hold null and 0. Swift maps each status to its own `CoreRenderError` case, and an unrecognised status to `unknownStatus`.
- `GenomeError` covers malformed hex (`InvalidHexLength`, `InvalidHexDigit`).
- The Swift and TypeScript tree decoders throw on an unknown tag or role, a missing field, a fraction where an integer belongs, or a `mask_ref` that breaks the mask table's rules (out of range, pointing to its own or a later entry, or leaving an entry unreferenced). Both decoders also refuse unknown fields. A silently defaulted primitive would draw a wrong creature that looks right.
